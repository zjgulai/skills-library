**教训（新增 5 条）**
1. **证据目录要按档位分**：`opt-loop.mjs run` 给 capture/wake-check/live 打印的是同一个 `evidence-rN`；若照抄，第二轮会**静默 skip**（有记录就不重跑）⇒ 看起来"绿"其实没跑。本轮 wake-check 首次就踩到（`evidence-r85` 里仍是 capture 的两条）⇒ 立刻改成 `evidence-rN-capture` / `-wakecheck` / `-live` 三目录并把那次绿判作废重跑。
2. **判据要挑能分辨的那个量**：给"倒排索引真的生效"写测试时，先写的是墙钟（4000 SKU 秒级）——去掉预筛选仍然 1.15 s **不会红**（假绿）。改成**数配对数**（`jaccard_overlap` 计数 ≤ 全量的 10%）后，去掉预筛选立刻红（1,999,000 vs 199,900 的界）。墙钟依赖机器快慢，计数不依赖。
3. **"文档承诺了但实现没有"是判者点名的真缺陷类**：`>10000 启用倒排索引` 写在错误处理表里、代码里却没有（r85 判者按 info 点名，r86 变成加分项）。本轮把它实现掉，比删承诺更好——承诺本身就是这个技能的性能卖点。
4. **版本跳跃无留痕时不要编造**：库内版本线从 1.1.0 直接到 2.2.0（模板时代由外部项目维护），判者按"版本审计断裂"扣分。正解是 2.2.0 写实、2.0–2.1 显式标「未留痕＋可从实现核对的既有事实」，而不是补两个假日期。
5. **同一技能允许"两轮 live"**：bucketer 走的是 基线 → 复评（94.5/83.5，带 8 条可修项）→ **按判者意见修完再评**（97.5/93.5）。轮内追加一轮是有成本的（27 请求），但对"文档与实现口径"这类点名项，修完再读一次比带着 83.5 写回更划算。
