## 5. C 轮：回合续跑语义（只读代码 + 无出境自测）

**代码事实**（`dsh-agent-loop/lib/index.js`）：
- `step()` 一旦执行就必然发起一次模型请求（`prepareRequest` → `llm.stream`）；
- 回合循环（`turn()` 934—975 行）里，`stepEnd === null` 才继续下一步；`stepEnd` 为 `{kind:'completed'}` 时会话若无 `next-step` 待办就收束回合；
- `stepEnd` 何时为 `completed`：1100—1119 行——助手消息**没有** tool-call 时，或 `executeToolCalls` 返回 `concluded === true` 时；
- `concluded` 的唯一来源是工具结果带 `concludesTurn: true`（`dsh-tools:3437/3480`，由工具体调用 `exec.concludeTurn()` 或 PTC 路径设置；`dsh-tool-cordis` 的文档明确写"a tool result carrying `concludesTurn` ends the turn at its step"）。我们的三个试用工具从不设置它。

**无出境自测**（runner 内置 `self-test`，在**同一张图**上：同样的八项服务 + pi-ai + 凭据层，仅把 adapter 换成脚本化的 provider）：
```text
self-test: {"outcome":"idle","calls":2,"continued":true}
```
即"带 tool-call 的回合 → 工具执行 → 第二步再发一次请求"在本装配下**确实发生**。

**结论**：装配与循环语义没有问题；首轮真实运行在两次 `trial_read` 之后即收束，差异只能来自**真实 provider 返回的数据形态**（例如中转把带 tool_calls 的 finish 上报成 `stop` 之外的值，或块/工具调用的组装方式）。判定这一点需要真实运行的原始数据。

**已就绪的仪表**（下次运行会写进记录，均为元数据，不含内容）：`stream_kinds`（收到的 chunk 类型序列）、`finish_kinds`（每次 finish 的 kind）、`observed_errors`（`agent/request-error` 等事件）、`self_test`（本轮自测读数）；运行前若自测未续跑，runner 会**拒绝消耗真实请求**。

## 7. 诊断轮（全部零出境）与驱动路径切换

**观测通道的盲区（本轮实测）**：`agent/*` 事件在**根上下文收不到**（扩宽订阅后整轮驱动期间一条未触发，而 `phase` 探针证明驱动确实启动了：`idle → running → idle`）；`session.eventsSnapshot` 与 `inbox.nextTurn` 访问器恒为空；会话持久化 JSONL 只落头部。**教训**：判断回合行为必须直接读句柄内部（`handle.phase`），不能依赖事件订阅推断"驱动没启动"。

**`kick()` 会静默吞掉回合错误**（`dsh-agent-loop:870-884`，`catch (_error) {}`）——这是所有"无声收束"读数的共同解释：回合里抛出的异常不会冒泡到调用方，也不会进入我们订阅的事件。

**已排除的因素**（每项都有零出境对照）：推理设置（代理级与路由级）、事件订阅宽度、`pi-ai` 挂载（跳过挂载后同样失败）、自测会话（跳过自测后同样失败）、预算预耗尽探针本身。

**根因定位到驱动序列本身**：同一张图、同一控制层，在 T08 的测试夹具里能稳定驱动回合（275 项测试多轮全绿），而在我的脚本 runner 里同样的 `create → install → send` 次序会让回合在第一次 `preStep` 即收束（与 `turn()` 946 行"step 0 且无消息 → 立即完成"一致）。差异尚未收敛到单行代码，**因此按计划改用已证明的驱动路径**。

**新载体**：[tests/t09-live.test.mjs](../../../skill-lifecycle/tests/t09-live.test.mjs)——把真实回合搬进 T08 风格的测试夹具，三档模式由 `T09_LIVE` 控制：

- `live`：D19 已批准的那一次真实任务（读两份输入 → 计算 → 写报告），运行前后比对 settings 哈希，并把 `stream_kinds/finish_kinds/audit/attempts/产物` 写入 `trial-home/evidence/t09-live-<ts>.json`。

**补记（同轮修动的生产代码）**：`control/dsh-plugin.mjs` 的 `budget.reserve` 现在被 try/catch 包住并记 `{kind:'request_denied', reason:<错误码>}`——此前"预留被拒"（如 `REQUEST_TOO_LARGE`/`ATTEMPTS_EXHAUSTED`）**不落审计**，既让零出境门禁无法区分"包装器拒绝"与"回合没到包装器"，也是审计链上的真实缺口。该改动使 dsh-plugin 的哈希离开 T06/T08 记录值（历史证据保留原哈希，不回写），本轮 275 项本地测试回归通过。

**对分结论（零出境）**：`pi-ai` 挂载本身不影响脚本化回合（4/4 通过）；此前"真实路由没走到包装器"的判断源自上面那个审计缺口，需在补记后以门禁重跑复核。

**门禁（零出境）**：`T09_LIVE=wake-check` **4/4 通过**，其中 `the real route reaches the model boundary and the wrapper refuses it` 证明真实 vod 路由确实走到包装器并在派发前被拒（账本零预留）。此前"真实路由没到包装器"的判断**撤回**——那是审计缺口造成的误判（现已补上预留失败的留痕）。同时 `mounting pi-ai alone does not break a scripted turn` 证明 pi-ai 挂载本身无副作用。
