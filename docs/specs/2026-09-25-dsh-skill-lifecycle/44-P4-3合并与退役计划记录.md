# 44｜P4-3 合并与退役计划（2026-09-27）

按 [34-P2–P4 工程化计划](34-P2P4工程化计划.md) 实施，P4 的收尾步骤。**纯工程、零真实请求、零写入**：本步只产出计划，不执行任何变更，账本也不追加（无技能版本处置发生）。

## 1. 交付物

`control/change-plans.mjs`：`planRetire()`／`planMerge()` —— **只产出计划**，模块不碰文件系统、不碰账本、不碰已安装技能。计划里显式带 `execution: { channel: 'enablement', automatic: false }`：执行仍走 P3 的启用/回退通道，且必须由用户拍板。

**退役 `planRetire({ heads, skillId, version, replacement, reason, evidenceRefs, dependents?, migration?, now? })`**

- **必须给替代**，且只有两种合法形态：
  - `{ skillId, version }` 继任版本——且**继任者自己必须"在用"**（链头是 `promote`／`retain`），否则 `REPLACEMENT_NOT_IN_USE`。要退役 A 交给 B，前提是 B 自己已经被验证并留下过处置——先后顺序被机制钉住；
  - `{ drop: true, reason }` 显式声明"这项能力就是不要了"——`reason` 必填。
  "回头再想"不是计划：缺替代、替代指自己、`drop` 没写理由，一律 `REPLACEMENT_REQUIRED`。
- 该版本账本链头已是 `retire`／`merge`／`rollback` → `ALREADY_OUT_OF_USE`（没有东西可退役）；账本**不认识**这个版本 → 允许出计划，但在 `ledger: { known: false }` 里记明，不假装它被验证过。
- **有依赖就必须有迁移说明**：`dependents` 非空而没给 `migration: { note, evidenceRef }` → `MIGRATION_REQUIRED`（谁还在用，得给个说法）。

**合并 `planMerge({ heads, source, target, reason, evidenceRefs, dependents?, migration?, now? })`**

- **双向引用写全**：`references.sourceToTarget = { from, mergedInto }` 与 `references.targetToSource = { into, absorbs: [from] }`——从任何一侧读到的都是同一个事实。
- 目标必须**在用**（`TARGET_NOT_IN_USE`）：并进一个从没被验证/处置过的版本是最典型的错；源不能是自己（`MERGE_INTO_SELF`）；源已不在用 → `ALREADY_OUT_OF_USE`（无物可并）。
- 源在账本里未知同样只记录不拒绝；依赖与迁移规则同退役。

**共同形状**：`planType`／`target`（或 `source`+`target`）／`reason`／`evidenceRefs`／`impact: { dependents, migration }`／`ledger`（**引用账本条目的 `dispositionId`**，不复制处置内容）／`execution`／`plannedAt`／**`planId`**（键排序规范形 sha256，供审批与后续账本条目引用）。全部 freeze；输入严格校验（字段集、id/版本形状、理由非空、证据指针 ≤500 字符且 ≤32 条、依赖条目两字段、`now` 整数）。

## 2. 验证

`tests/change-plans.test.mjs`，**9 项全绿**：退役计划形状（`planId`、替代方向、账本证据指向真实 `dispositionId`、`execution.automatic === false`、冻结、`plannedAt`）、缺替代/自指/无理由 drop 三态全拒＋合法 drop 通过、已不在用再退役拒＋账本未知只标注、继任者必须在用（未知与已退役两种）、合并双向引用逐字段、并入未验证目标/自身/源已退役三拒、有依赖无迁移拒（退役与合并各一次）＋给了迁移即记录、输入校验（坏 heads/理由/证据/依赖/`now`/多余键）、**计划零写入**（真账本 + 真目录：跑完计划后账本字节不变、目录清单不变）。

**变异验证**（6 处，每处只打中对应用例）：

| 去掉"已不在用不可再退役" | 1 红：重复退役用例 |

**真实账本 dry-run**（只读）：拿项目内唯一链头（`validate-data@original-1e424822`）——不带替代直接拒（`REPLACEMENT_REQUIRED`）；显式 drop 出计划（`planId 7a23ead0…`，`ledger.dispositionId` 指向账本里那条真记录 `03bd4e49…`）；把未验证版本当合并目标 → `TARGET_NOT_IN_USE`；源未知则只记录不拒。**计划本身不落盘**：这些读数全部来自内存中的返回值。

全量回归：**435 项通过**（此前 426），`exit=0`，输出落档 `/tmp/p4-3-full-regression.txt`。

## 3. 边界

- 计划 ≠ 执行：本模块没有任何写路径；真正启用/回退仍走 `control/enablement.mjs` 的 `planEnable → applyEnable → rollbackEnable`，且已有它们各自的授权门。
- **依赖事实由调用方给**（`dependents`）——项目里还没有技能依赖图，这里不发明一份；只保证"有依赖就必须要迁移说明"这条规则成立。
- 退役的账本落档：真正执行退役/合并后，按「随步累积」策略往账本追加 `retire`／`merge` 处置，并可用 `planId` 引用本计划。
- 未做：计划与账本的自动对账（计划批准后由谁执行、执行后账本是否已记），留给真正做第一次退役时按需补。
