# 41｜P2-3 新技能接入同一评测链（2026-09-27）

按 [34-P2–P4 工程化计划](34-P2P4工程化计划.md) 实施。**纯工程、零真实请求**：本节只证明"新技能能被同一条评测链比较"，不铸造真实终测集、不产生真实运行。

## 1. 交付物

「评测链的 arm 词表加 `none`（无技能臂）＋新技能的终测题型」拆成四处落地：

### 1.1 共享词表 `control/arm-scope.mjs`（新）

- `armVocabulary = ['original','none','candidate']`；`baselineArms = ['original','none']`——两个基线**互斥**，一轮只能比一个。
- `noSkillDigest = sha256('arm-scope:no-skill-armed')`：**缺席哨兵**。控制层（`run-state`／`budget-ledger`／`dsh-plugin`）要求 binding 的每个摘要都是 64 位十六进制，用 `null` 会被读成"字段缺失"而不是"故意的无技能"；所以无技能臂带一个任何审计都能重算的固定值，且**绝不等于任何真实技能文件哈希**。
- `normaliseArms(arms)`：集的臂策略校验与规范化（基线在前、candidate 在后）；`assertArmAllowed(arms, arm)`；`isArmed(arm)`；`toolScopeFor({armed})`＝有技能 4 工具（含 `skill`）／无技能 3 工具。
- 该模块没有独立测试文件，规则由三个消费者各自的用例覆盖（见 §4）。

### 1.2 迭代控制器 `control/iteration-loop.mjs`

- 观测词表接受 `none`；新增 `baselineArm` 选项，**基线由记录自身推导**（`original` 与 `none` 由构造互斥，出现两个即拒），显式传入只允许与记录一致，不允许相反——`INVALID_OBSERVATION`。
- 三条停止条件（主效应／回归／成本容差）与基线角色解耦：`none` 基线上跑的是同一套逻辑，不存在"换个臂就走另一条判定"的分支。
- `metrics.attempts/tokens` 的基线键由 `original` **改名为 `baseline`**，并新增 `metrics.baselineArm`。历史 round 文件（`trial-home/a4/rounds/round-*.json`）保持写入当时的形状，不回写。

### 1.3 执行前门 `control/preflight.mjs`

- manifest 可声明可选 `arm`；未知值 → `INVALID_MANIFEST`。
- `arm: 'none'` 时工具范围为 3 项（少 `skill`）：仍声明 `skill` → `TOOL_NOT_ALLOWED: skill`；缺任一工具 → 既有 `TOOL_MISSING`。
- 无技能臂仍带 `skill` 材料（declared 或 approved 任一）→ `UNARMED_SKILL_MATERIAL`。
- **摘要与臂必须配对**：无技能臂必须带缺席哨兵，有技能臂必须不带——`(skillDigest === noSkillDigest) === skillArmed` 成立即 `SKILL_DIGEST_SCOPE_MISMATCH`，两个方向都拦。

### 1.4 终测集策略 `control/terminal-set.mjs`

- `sealTerminalSet` 新增可选 `arms`，默认 `['original','candidate']`（已有 `w01`/`w02`/`w03`/`v1` 的封存清单没有该字段，按默认读，**不追改封存件**）。
- 只接受两种形态：`['original','candidate']`（已有技能）或 `['none','candidate']`（新技能）；两条基线、只有一条、或其他组合一律 `INVALID_ARMS`。
- `openTerminalSet` 暴露 `arms`，载体据此拒绝不该跑的臂。

### 1.5 终端载体 `tests/terminal-run.test.mjs`

`T_ARM=none` 的装配（"不挂技能根"）：

- 不挂 `dsh-skill` 注册表、不挂 `dsh-skill-filesystem`、不挂 `dsh-tool-skill`；`skillRoot` 仍作为第三根存在但**必须为空**（`openFiles` 要求三根互斥）。
- 工具白名单与 `installTrialControl` 都不含 `skill`（不传 `allowedSkillNames`，控制层因此不注册也不放行该工具）。
- 提示词不含"加载技能"指令；脚本化 dry-run 不含 `skill` 调用；`openFiles`／preflight 的 `files`／`approvedFiles` 都不含 `skill` 文件。
- 运行期断言：`ctx.tools.get('skill', handle)` 必须与臂一致——**有技能臂为真、无技能臂为 undefined**。
- 记录新增并可审计：`skill_armed`、`skill_tool_visible`、`tool_scope`、`terminal.prompt`（组装后的完整提示词）；`skill_digest`／`candidate_id` 在无技能臂为 `null`；`incomplete` 逐臂计算（无技能臂不因"没加载技能"算不完整）。
- 集策略在执行前生效：`assertArmAllowed(terminalSet.arms, arm)`——拿 `none` 跑 `w01` 直接 `ARM_NOT_ALLOWED: none`（已实测）。
- 新增 `T_SET_ROOT`，**仅 capture 可用**：`T_MODE=live` 时一旦设置即拒绝（真实运行只能读 `trial-home` 托管区）。

## 2. 「新技能的终测题型」的落点

新技能终测集 = `arms: ['none','candidate']` 的封存集：题目是"该技能应当处理的请求"，比较对象是"装了这个新技能"对"完全没有技能"。载体、前门、控制器、集策略四处一致，因此**同一条链**既能评已有技能（`original` vs `candidate`），也能评新技能（`none` vs `candidate`），不需要第二套判定逻辑。

## 3. 明确的取舍

- **本轮不铸真实新技能终测集**：铸造要走 [32 号](32-w03终测集铸造记录.md) 的封存流程（材料→独立审料→封存），而 P2 链上还没有具体的新候选；先造一个没有对应候选的"终测集"只会多一份无主封存件。演练用**临时集根**（`T_SET_ROOT`）在测试内自铸自闭，`trial-home/terminal` 不被污染。
- **缺席哨兵而非 `null`**：代价是"无技能"也有一个摘要值，收益是控制层（run-state／预算／审计）不需要为一种臂开特例，且这个值可被任何审计重算比对。
- **`metrics` 改名**：`attempts.original` → `attempts.baseline`，并加 `baselineArm`。改名是为了不让一个叫 `original` 的键装 `none` 的数；历史 round 文件不回写。

## 5. 过程中发现的问题（值得记住的坑）

**嵌套 `node --test` 会静默零输出**：在 `node --test` 里派的子进程若继承 `NODE_TEST_CONTEXT`（值 `child-v8`，另有 `NODE_TEST_WORKER_ID`），子 runner 不产出任何结果、退出码仍是 0——表现为"子进程成功但 stdout 为空"。修法：派发前删掉这两个变量。本轮无技能臂演练正是靠这个才跑通（先在 `/tmp` 用最小探针复现确认，再修）。

另外两处是载体自身的真缺陷：`runTask` 无条件创建 `skill-root/validate-data`；`openFiles` 无条件登记 `skill` 文件——无技能臂下前者让"空技能根"断言失败、后者直接 `UNSAFE_FILE`。都已改为按臂装配。
