# 38｜P3-3 回退与"不混中间态"（2026-09-27）

按 [34-P2–P4 工程化计划](34P2P4工程化计划.md) 实施。**纯工程、零真实请求**；目标只限 `trial-home`。

## 交付物（`control/enablement.mjs` 扩展）

**1. 落盘备份（让回退能跨进程）**
`applyEnable({ …, backupRoot })` 在落地**之前**写 `<backupRoot>/<skillId>@<ts>/{manifest.json, files/**, IN_PROGRESS}`：manifest 记录安装前的每个文件摘要；`IN_PROGRESS` 是"这次安装还没做完"的标记。成功后清标记，回执里登记 `backupId`。备份根必须落在允许目录内（`BACKUP_OUT_OF_SCOPE`）。

**2. 再入保护**
`assertNoInstallInProgress({ backupRoot, skillId })`：只要该技能还有带 `IN_PROGRESS` 的备份目录就**抛** `INSTALL_IN_PROGRESS`，`applyEnable` 在开跑前调用它 → **有半成品就拒绝新安装**（不同技能互不阻塞）。

**3. 显式回退**
`rollbackEnable({ allowedParent, root, skillId, backupRoot, receiptRoot, installId?, now, afterRestore })`：
- 只读磁盘备份即可回退（不需要任何内存状态）→ **跨进程可用**；备份根不存在报 `NO_BACKUP`，指定的 installId 找不到报 `UNKNOWN_BACKUP`，备份文件自身被改报 `BACKUP_FILE_CHANGED`。
- **回退自身也可见**：开始时就写 `phase: 'rollback'` 的标记，**成功才清**——崩在回退中途也会留下"未完成"的痕迹。
- 恢复后**逐文件核验**：不一致即 `ROLLBACK_VERIFY_FAILED`，且**保留标记**（绝不让状态看起来是干净的）。
- 成功则写**回退回执**（`restoredDigest`、`recovered` 标志——即这次回退是否救的是一个"未完成安装"），已存在的回执不被覆盖。

## 验证（`tests/enablement.test.mjs`，21 项全绿）

| 用例 | 断言要点 |
|---|---|
| 备份 + 跨进程回退 | 回执登记 `backupId`；成功后无 `IN_PROGRESS`；**只凭磁盘备份**回退 → 树精确恢复为安装前状态；回退回执 `verified: true` |
| 崩溃残留 | 人为留下 `IN_PROGRESS` → 新安装被拒（`INSTALL_IN_PROGRESS`）→ 对其回退 → `recovered: true` 且标记被清 |
| 失败路径自愈 | 注入"落地后抛错"→ `INSTALL_APPLY_FAILED`，且标记被清（状态是干净的） |
| 回退核验失败 | 注入"恢复后被改"→ `ROLLBACK_VERIFY_FAILED`，**标记留下**且写明 `phase: "rollback"` |
| 无备份可回 | 备份根不存在 → `NO_BACKUP`；指定不存在的 installId → `UNKNOWN_BACKUP` |
| 根越界 | `backupRoot` 在允许目录外 → `BACKUP_OUT_OF_SCOPE` |

全量回归：**388 项通过**（此前 383）。

## 实施中的两处调整（都记在案）

1. **语义修正（产品侧）**：备份根**不存在**时，`readBackup` 原本报 `INVALID_BACKUP_ROOT`；对"回退"这个动作来说，"没有备份"才是真实语义 → 改为 `NO_BACKUP`（存在但不是目录才仍是 `INVALID_BACKUP_ROOT`）。
2. **回退标记（产品侧）**：原设计只在"安装进行中"留标记；实测发现"回退失败后无痕迹"会让状态看起来干净。改为**回退也自标记**，失败即保留——这正是"不混中间态"的应用。
