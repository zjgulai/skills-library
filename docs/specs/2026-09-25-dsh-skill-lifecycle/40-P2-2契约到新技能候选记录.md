# 40｜P2-2 契约→新技能候选（无源版）（2026-09-27）

按 [34-P2–P4 工程化计划](34-P2P4工程化计划.md) 实施。**纯工程、零真实请求**，目标目录只限项目内候选区。

## 交付物

`control/draft-candidate.mjs`：`openDraftCandidate({ root, candidateId, contract, hypothesis, affectedScope, name, description })` → 无源版候选句柄（`preview` / `writeDraft` / `seal` / `verify` / `manifest`）。

与 W1 `skill-candidate`（已有技能优化）的关键差别：**没有 source 就没有 `sourceDigest`**，身份改绑到 P2-1 的**契约摘要 `contractDigest`**。新技能的风险不是"改坏了原版"，而是"没写进契约就该有的东西"。计划里要求的"差异说明"在无源场景下的对应物 = **新增文件清单（逐文件 sha256）＋约束覆盖检查＋`hypothesis`/`affectedScope`**，一并进清单 `candidate.json`。

- **准入**：契约必须 `verdict === 'draftable'`，六字段齐全，`constraints` 至少 1 条（否则 `CONTRACT_NOT_DRAFTABLE` / `INVALID_CONTRACT`）。签名要求 `name` 命中 `^[a-z0-9][a-z0-9-]{1,63}$`，`hypothesis` 恰两键且非空，`affectedScope` 非空。
- **草稿文件约束**：必须含 `SKILL.md`；≤16 个文件、单文件 ≤64 KiB；相对路径字符集受限且禁 `..` 与绝对路径；内容须为合法 UTF-8。
- **写盘时的三条绑定**（任一不满足即拒，且**一个字节都不落盘**）：
  1. frontmatter 的 `name`/`description` 必须等于声明的值（`SKILL_NAME_MISMATCH` / `SKILL_DESCRIPTION_MISMATCH`）——候选不得自我改名；
  2. **每条契约 `constraints` 必须逐字出现在 `SKILL.md` 里**（`CONSTRAINT_NOT_COVERED: <条目>`）——这是"新技能静默丢掉安全约束"的直接拦截；
  3. 落盘走临时文件 + rename。

  > `description` 由调用方传入、与 `SKILL.md` 逐字比对，是因为它在 DSH 里同时是**触发面**：改写触发语等于改写技能的作用范围，属于契约变更而非编辑自由。
- **封存与不可变**：`seal()` 后 `writeDraft` 一律 `CANDIDATE_SEALED`；未写过就封存是 `CANDIDATE_NOT_WRITTEN`。
- **`verify({ contract })`**：先比 `contractDigest`（`CONTRACT_CHANGED`），再**递归**清点草稿树与清单逐路径对齐（`CANDIDATE_FILE_SET_CHANGED`，符号链接等非文件项直接拒），再逐文件比 sha256（`CANDIDATE_FILE_CHANGED: <relPath>`），最后整体摘要（`CANDIDATE_IDENTITY_CHANGED`）。通过则返回 `{ ok, checks: ['contract','file-set','digests'], contractDigest }`。

## 本轮修掉的两个真实缺陷

初版两次跑出 2 红（`TypeError: Cannot read properties of null (reading 'map')`），定位到两处实现错误，都不是测试写错：

1. **`persistManifest` 每次重建清单都会把 `files` 置回 `null`**——`writeDraft` 写入的文件清单在 `seal()` 第二次落盘时被抹掉，于是任何"封存后 verify"都崩。改为由闭包状态 `writtenFiles` 单一供源，`seal()` 只叠加 `sealed/sealedAt`。
2. **文件集比对只取 basename 且 `readdir` 不递归**——草稿含嵌套文件（如 `refs/checklist.md`）时，声明侧出 `checklist.md`、盘上侧只出顶层项，永远对不上。改为递归遍历、按**完整相对路径**排序比对。

## 验证

`tests/draft-candidate.test.mjs`，**9 项全绿**：happy path（写→封→验＋清单 schema）、非 `draftable` 契约拒、改名/改描述拒、约束未覆盖拒、文件校验（空集/缺 `SKILL.md`/越界路径/超长，且**落盘前失败不留文件**）、封存后写入拒＋篡改检出、嵌套文件完整性（干净可验→改内容检出→**还原字节即恢复身份**→新增嵌套文件检出）、契约变更后 verify 拒、id/hypothesis/scope 校验与 `CANDIDATE_EXISTS`。

**变异验证**（证明这些断言不是假绿）：

| 注入的旧缺陷 | 结果 |
|---|---|
| `files: null`（缺陷 1 复发） | 3 红：happy path、封存后篡改、嵌套文件完整性 |
| basename 比对（缺陷 2 复发） | 2 红：happy path、嵌套文件完整性 |

两次变异都只打中 verify 相关用例，其余用例保持绿——说明覆盖点集中在被测维度上，未误伤无关路径。变异后已还原，行为以当前实现为准。

## 边界

- 本轮只产出**候选与清单**，不安装（安装属 P3-1..P3-4 通道）、不评测（评测属 P2-3）——"生成目录 ≠ 能力证明"仍然成立。
- 约束"逐字覆盖"是**存在性检查**，不是语义等价检查：它拦得住"整条丢"，拦不住"写了但不照做"。后者只能由终测集发现，不在本模块能力边界内。
- `verify` 的权威源是"清单 + 盘上内容"，不校验 `SKILL.md` 的 frontmatter 是否仍与声明一致（写完即封存后 frontmatter 已被 sha256 锁住，改了就报 `CANDIDATE_FILE_CHANGED`）。
