# 37｜P3-2 安装与核对（2026-09-27）

按 [34-P2–P4 工程化计划](34P2P4工程化计划.md) 实施。**纯工程、零真实请求**；目标只限 `trial-home`。

## 交付物（`control/enablement.mjs` 扩展）

**`applyEnable({ plan, allowedParent, root, skillId, candidate, previous, receiptRoot, now, afterApply })`**

1. **先验计划**：`verifyPlan()` 重新推导，`planDigest` 不一致 → `PLAN_CHANGED_SINCE_PREVIEW`（什么都不写）。
2. **落地**：新增/替换文件先写临时名再 `rename`（逐文件原子）；删除计划中的 `removed`。
3. **落地前状态留底**：把已安装树的**全部内容**读进内存（≤64 文件 × ≤256KB），作为回滚基准。
4. **核对（关键）**：落地后**重新整树读取**并与候选声明逐文件比对；不一致即 `INSTALL_VERIFY_FAILED`。
5. **回滚**：任何失败路径（落地异常 `INSTALL_APPLY_FAILED` 或核对失败）都调用统一的 `restoreTree(root, before)`——**删掉 before 里没有的、把 before 里的全部写回**，恢复为精确的原状态。
6. **安装回执**：`{skillId, candidateId, installedAt, planDigest, previousDigest, installedDigest, verified, files[]}`，写入 `receiptRoot`；`receiptRoot` 必须在 `allowedParent` 内（`RECEIPT_OUT_OF_SCOPE`），且**已存在的回执不被覆盖**（`RECEIPT_EXISTS`，实测原文件字节不变）。

**注**：`afterApply` 是**故障注入缝隙**（仅测试使用，生产不传）——没有它，"落地后被改"这条分支无法被证明会红。

## 验证（`tests/enablement.test.mjs`，16 项全绿）

| 用例 | 断言要点 |
|---|---|
| 首次安装 | 落地后整树摘要 == 候选声明；回执写出且 `verified: true` |
| 升级 | 替换 + 删除都生效；落地后树只剩候选文件 |
| **注入"落地后被改"** | 核对真的会红（`INSTALL_VERIFY_FAILED`）；**树被精确还原**到原状态；**失败不留下回执** |

| 候选文件失配 | 候选声明与磁盘不符 → `CANDIDATE_FILE_CHANGED`，**一个文件都没写** |
| 回执越界 | `receiptRoot` 在允许目录外 → `RECEIPT_OUT_OF_SCOPE` |

全量回归：**383 项通过**（此前 376）。

## 实施中的两条诚实记录

1. **我方测试助手藏了一个假绿**：`snapshotOf()` 里 `try { … } catch { /* absent */ }` 会把**真实错误**（`readdir` 未导入的 `ReferenceError`）也吞掉，导致断言拿到空对象、看起来像"没装成功"。已改成**只忽略 `ENOENT`**。（教训：测试助手里的裸 `catch` 会制造假绿，与"不会红的检查不是检查"同类。）
2. **一处期望值写错**：把"预览后候选变了"的用例写成期待 `CANDIDATE_FILE_CHANGED`，实际产品行为是 `PLAN_CHANGED_SINCE_PREVIEW`（候选对象已与新状态一致，计划身份变了）——**产品行为是对的**，已修期望，并**另补**一条真正走 `CANDIDATE_FILE_CHANGED` 的用例。
