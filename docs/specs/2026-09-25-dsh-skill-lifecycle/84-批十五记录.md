## 批十五·仪器修复：版本一致性扫描器三处收紧

起因＝skill 3 的 `- **版本管理**：本版本 v1.0.1，历史版本见 git 记录` **被判者抓到而扫描器放过了**（我这边 0 处、判者 warning）。三处修复（都在 `trial-home/screening/version-consistency.mjs`）：

1. **历史豁免从"整行"改为"命中点窗口"**（±40/60 字符）：旧实现里一行结尾随便出现 `deprecated` 就会把行中的版本残留一起豁免（批十四的 `标deprecated` 那次）。
2. **「本版本/当前版本/版本：」当前版本声明不受历史豁免**：否则「本版本 v1.0.1，历史版本见 git 记录」这种"当前声明 + 历史提及"同句的写法永远漏检（本轮实测）。
3. 顺带修正：豁免只作用于扫描器内部，读侧不再做整行 HISTORICAL 判定（避免两处口径打架）。

**收紧后全库读数由 13 处修正为 12 处 / 8 技能**——少的那处正是同类残留（说明收紧同时提高了**召回**）。

**教训（新增 3 条）**
1. **"跑一遍用户路径"要在**改之前**跑**：logistics 的 CLI 崩溃（裸 `%`）与两张"未实现参数/不存在的夹具"都是**先跑一次示例命令**就当场暴露的；批十五三件里两件的头号 error 是这么发现的。
2. **依赖声明要看真身**：judge 说"依赖 pandas"——core 是纯标准库，但 **CLI 确实是硬依赖**。教训不是"judge 错了"，而是**同一条链上不同层可以有不同的依赖事实**，判决前把每一层都跑一遍（本轮把 CLI 也去依赖了）。
3. **豁免规则也是判据**：扫描器连续两轮"该报没报"（窗口过宽、当前声明被历史词吃掉）。修扫器本身要**先复现漏检、再改、再复扫全库看召回与误报是否同向改善**（本轮 13→12 处说明收紧同时抓到了新残留）。
